## Autenticação e sessão do administrador

- [x] CHK001 Os requisitos de armazenamento e de política de senha estão definidos de forma mensurável (classe do algoritmo e custo do "hash forte", sal por senha, tamanho máximo, tratamento de senhas triviais) ou adiados ao plano com responsável explícito, dado que esta conta enxerga todos os alunos da escola? [Clarity, Spec §FR-004, Assumptions]
- [x] CHK002 A ausência de segundo fator de autenticação para o administrador está registrada como decisão consciente, com o risco residual aceito? [Gap, Spec §FR-004]
- [x] CHK003 Estão especificados o transporte e a guarda da sessão (cookie inacessível a scripts, somente HTTPS, proteção contra requisição forjada entre sites, novo identificador a cada login) e se o mesmo administrador pode ter várias sessões simultâneas? [Gap, Spec §FR-005]
- [x] CHK004 O "na hora" da revogação (inativar, reemitir código, desvincular, "Sair") tem limite mensurável, inclusive para requisições já em andamento? [Measurability, Spec §FR-014, FR-030, FR-033, SC-010]
- [x] CHK005 Existe requisito para o administrador autenticado trocar a própria senha, com o efeito sobre as suas outras sessões? [Gap, Spec §FR-032]
- [x] CHK006 Está definido se as ações destrutivas e de acesso exigem só confirmação em diálogo ou também reautenticação, e a razão da escolha? [Clarity, Spec §FR-009]
- [x] CHK007 A normalização do e-mail do administrador (maiúsculas, espaços nas pontas) está especificada, como foi para o professor? [Gap, Spec §FR-010, FR-032]

## Emissão e proteção de credenciais (ativação, acesso, primeiro administrador)

- [x] CHK008 O código de ativação do administrador tem formato, tamanho/entropia, forma de apresentação na Web (sozinho ou com e-mail), limite de tentativas contra adivinhação e regra de que um código novo invalida o pendente? [Gap, Spec §FR-032, FR-033, FR-034]
- [x] CHK009 O FR-032 ("ninguém conhece ou define a senha de outro") entra em conflito com o fato de o administrador que cria a conta ver o código de ativação e poder usá-lo antes do destinatário? Há requisito que impeça ou torne detectável esse uso? [Conflict, Spec §FR-032, US7-1]
- [x] CHK010 "Guardar de forma não reversível" está definido considerando o espaço pequeno dos códigos (8 caracteres), por exemplo exigindo resumo com chave secreta em vez de resumo simples? [Clarity, Spec §FR-011]
- [x] CHK011 A exibição única dos códigos tem requisitos de proteção (fora de URL, histórico, cache e log) e a entrega ao destinatário fora do sistema está registrada como premissa ou risco aceito? [Gap, Spec §FR-011, US2-1]
- [x] CHK012 O procedimento do primeiro administrador define quem pode executá-lo (fronteira de confiança) e o que acontece quando é executado com um e-mail novo em ambiente que já tem administradores? [Gap, Spec §FR-034, US8]
- [x] CHK013 A recuperação de acesso define o efeito sobre as sessões e sobre a senha atual do administrador recuperado? [Gap, Spec §US8-3]

## Separação de papéis e autorização

- [x] CHK014 Existe uma matriz de permissões única (operação × papel × canal) da qual o teste de acesso cruzado do SC-005 possa ser derivado, em vez de regras espalhadas pelas histórias? [Traceability, Spec §FR-002, FR-003, SC-005]
- [x] CHK015 A resposta a credencial de professor em rota administrativa na Web (e o inverso) está definida de forma consistente, indistinguível de rota inexistente, como a negativa neutra do Telegram? [Clarity, Spec §US1-5, FR-008]
- [x] CHK016 Está especificado o que ocorre quando a mesma pessoa mantém sessão de professor e de administrador no mesmo navegador (RN-14)? [Edge Case, Gap]
- [x] CHK017 "Indistinguível de aluno inexistente" está definido de forma mensurável (código de status, corpo, cabeçalhos, tempo de resposta, texto do bot)? [Measurability, Spec §FR-025, SC-006]
- [x] CHK018 A recusa por CPF já existente quando o professor EDITA o CPF de um aluno compartilhado (e não só no cadastro) tem a mesma resposta neutra, o mesmo registro de autoria e o mesmo tratamento de sondagem do FR-024? [Gap, Spec §FR-024, FR-026]
- [x] CHK019 "Único professor associado" (FR-026) diz se professores inativos contam, de modo que a regra de inativar aluno compartilhado não seja ambígua? [Ambiguity, Spec §FR-026]

## Bloqueio por tentativas

- [x] CHK020 "Mesma origem" está definida (endereço de rede? como é obtido atrás do proxy reverso? rede única da escola compartilhada por vários usuários)? [Ambiguity, Spec §FR-006]
- [x] CHK021 O requisito trata o risco de negação de acesso (alguém na mesma origem bloqueia o administrador legítimo) e a ausência de proteção por conta contra tentativas distribuídas em várias origens? [Gap, Spec §FR-006]
- [x] CHK022 Está definido se tentativas feitas durante o bloqueio prorrogam ou reiniciam os 15 minutos? [Ambiguity, Spec §US1-4]
- [x] CHK023 Tentativas com e-mail inexistente ou conta inativa contam do mesmo modo que senha errada, de forma que contagem e mensagem de bloqueio não revelem se a conta existe? [Consistency, Spec §FR-004, FR-006]
- [x] CHK024 A contagem sob tentativas simultâneas está especificada (requisições paralelas não podem ultrapassar o limite de 5), já que o FR-041 trata concorrência só de e-mail e CPF? [Gap, Spec §FR-006, FR-041]
- [x] CHK025 O limite de tentativas contra sondagem de CPF pelo professor está quantificado como requisito, e não apenas adiado ("o plano deve avaliar")? [Measurability, Spec §Assumptions]

## Tratamento do CPF

- [x] CHK026 Os requisitos de CPF cifrado e de detecção de duplicidade exigem uma representação de busca que resista a enumeração (o conjunto de CPFs válidos é pequeno) e cobrem a gestão da chave (separação do banco, rotação, cópias de segurança)? [Gap, Spec §FR-019, FR-020]
- [x] CHK027 A proibição de expor o CPF cobre também URL e parâmetros de consulta, cache, histórico e preenchimento automático do navegador, relatórios de erro e cabeçalhos, e não apenas "logs, API, telas e mensagens"? [Coverage, Spec §FR-020, FR-039]
- [x] CHK028 A exposição do CPF ao digitá-lo no Telegram (servidores e histórico do chat) está tratada: apagar a mensagem, aviso ao professor ou risco aceito, e restrição do fluxo a conversa privada (nunca grupo)? [Gap, Spec §Edge Cases, FR-036]
- [x] CHK029 A retenção de dados de execução do transporte (n8n) está coberta para atualizações que carregam CPF, e a autenticidade da chegada do webhook (spec 004) está registrada como dependência validada? [Dependency, Spec §FR-039, SC-004]
- [x] CHK030 O descarte do cadastro em andamento (com CPF cifrado) está exigido em todos os caminhos de revogação (inativar professor, reemitir código com encerramento do vínculo), e não só na desvinculação do FR-031? [Consistency, Spec §FR-014, FR-030, FR-031]

## Menores de idade e dados do responsável

- [x] CHK031 A coleta de dados de menores (inclusive CPF e nome do responsável) antes do consentimento do responsável (feature 007) está registrada como premissa com dependência de ordem de entrega ou risco aceito? [Dependency, Spec §Escopo]
- [x] CHK032 O fuso da escola usado para calcular a idade está identificado? [Clarity, Spec §FR-017, Edge Cases]
- [x] CHK033 A retenção do nome do responsável quando o aluno completa 18 anos, ou é editado para adulto, está definida (minimização)? [Gap, Spec §FR-017]
- [x] CHK034 O responsável está limitado ao nome (sem telefone, e-mail ou CPF) como exclusão explícita, e o requisito proíbe que esse nome siga para provedores de IA (Princípio IV)? [Completeness, Spec §Key Entities]
- [x] CHK035 Há limites de validação por campo (tamanho máximo e caracteres aceitos de nome, responsável, instrumento e e-mail)? [Gap, Spec §FR-017, FR-018]

## Mensagens de erro e não revelação

- [x] CHK036 A política de revelar o estado da conta é consistente entre papéis (administrador inativo = mensagem uniforme; professor com conta inativa ou código substituído = orientação específica)? [Consistency, Spec §FR-004, FR-014, FR-042]
- [x] CHK037 Estão cobertas as classes de falha: validação, autorização, duplicidade sob concorrência, confirmação vencida, operação parcialmente falha e indisponibilidade interna (mensagem genérica, sem detalhe)? [Coverage, Spec §FR-039, FR-045]
- [x] CHK038 Para o administrador, o que a recusa de duplicidade pode revelar (nome do aluno existente) está delimitado e justificado em contraste com a regra do professor? [Clarity, Spec §FR-010, FR-019]
- [x] CHK039 "Negativa neutra" do Telegram está definida de forma concreta (mesma resposta para conta vinculada ou não, sem sugerir que existe área administrativa)? [Ambiguity, Spec §FR-008, FR-037]

## Autoria das ações

- [x] CHK040 Os campos do registro de autoria estão enumerados, inclusive o identificador gravado em falha de login com e-mail inexistente e a justificativa (LGPD) para guardar e-mail ou endereço de origem? [Completeness, Spec §FR-040]
- [x] CHK041 Está definido se bloqueios, expiração de sessão, "Sair" e negativas de autorização (professor em rota administrativa, identificador de aluno alheio manipulado) geram registro, já que hoje só a recusa por CPF alheio gera? [Consistency, Spec §FR-025, FR-040]
- [x] CHK042 Está exigido que a gravação e o seu registro de autoria valham juntos, e o que acontece se o registro não puder ser gravado? [Gap, Spec §FR-040]
- [x] CHK043 Há requisito de integridade dos registros (somente acréscimo, sem alteração ou exclusão pela aplicação, quem pode acessá-los), mesmo com a consulta adiada à feature 007? [Gap, Spec §FR-040]
- [x] CHK044 A janela em que leituras de dados de aluno (administrador sobre toda a escola) ficam sem rastro até a feature 007 está registrada como risco aceito, com ordem de entrega? [Assumption, Spec §D9]
- [x] CHK045 O autor está definido para quem não é usuário Web (conta do Telegram, origem "carga inicial", mantenedor no procedimento do primeiro administrador), e o SC-014 consegue derivar a lista de operações que devem gerar registro? [Measurability, Spec §FR-044, SC-014]
